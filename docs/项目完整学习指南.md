## 1. 项目鸟瞰

### 一句话

> 在 Nuclei 扫描引擎之上集成 Ollama 本地 LLM，用"AI 语义分析 + 硬规则修正"的混合防线自动过滤误报，通过 Web 面板展示结果并生成中文安全报告。

### 核心数据

| 指标 | 数值 |
|------|:--:|
| 代码量 | ~2800 行 |
| 文件数 | 39 个 |
| 自定义模板 | 20 个（5 技法演示 + 15 漏洞检测） |
| 靶场端点 | 20 个（14 真漏洞 + 6 误报干扰） |
| AI 准确率 | 最终轮 100%（稳态 90%+） |
| 扫描耗时 | ~3-5 分钟 |

### 技术栈（面试版）

```
扫描引擎: Nuclei v3.8.0 (Go 编写，YAML 驱动)
指纹识别: httpx (Go 编写)
AI 推理: Ollama + qwen3:8b (Q4_K_M 量化)
后端框架: FastAPI (Python 异步)
前端模板: Jinja2
前端样式: 原生 CSS（深色主题，无框架依赖）
靶场: Python http.server（标准库，零依赖）
```

### 为什么选这些技术

- **Nuclei**: 社区最活跃的开源漏洞扫描器，YAML 模板生态丰富，3000+ 官方模板
- **Ollama**: 本地部署 LLM 的最简方案，一行命令拉模型，HTTP API 调用，零费用
- **qwen3:8b**: 中文理解能力好，8B 参数在消费级 GPU/CPU 上可运行
- **FastAPI**: Python 异步框架，自带 Swagger 文档，适合 API + 模板渲染
- **纯 CSS**: 不引入前端框架依赖，减少项目复杂度，面试展示原生能力

### 3.2 `core/ai_filter.py` — AI 过滤引擎（221 行）

**职责**: 批量调用 LLM + 硬规则修正，是整个项目的核心模块

**核心流程**:

```python
async def filter_results(results, ...):
    # 1. 分批次（BATCH_SIZE=5，平衡速度和准确性）
    for batch_start in range(0, len(results), BATCH_SIZE):
        batch = results[batch_start:batch_start + 5]
        verdicts = await _process_batch(batch, ...)

    # 2. 对每条结果应用 5 条硬规则修正
    for result, verdict in zip(results, verdicts):
        # 规则 1: tech 类型永不标误报
        # 规则 2: HTML 转义过的 XSS → 自动误报
        # 规则 3: 内部重定向 → 安全
        # 规则 4: Debug 已关闭 → 不暴露
        # 规则 5: Git 文字提及无文件链接 → 误报
```

**Prompt 结构**:

```
SYSTEM_PROMPT（系统提示词 — 角色 + 判定标准）
  ├─ 三类结果的不同判定逻辑
  │   ├─ 技术识别类: 不是漏洞，不标误报
  │   ├─ 漏洞利用类: 三种误报场景（教程页/转义/无关文本）
  │   └─ 配置暴露类: 两种误报场景（通用错误页/已关闭声明）
  └─ 输出格式: JSON 数组

BATCH_PROMPT（用户提示词 — 具体数据）
  ├─ {count} 条待分析结果
  ├─ {items} 每条结果的摘要（URL + 名称 + 标签 + 请求/响应）
  └─ 输出恰好 {count} 个对象
```

**关键设计 — 响应摘要函数**:

```python
def _summarize_result(result, index):
    # 构建给 LLM 看的数据摘要
    # 重要：HTTP 响应分头部和正文两部分
    parts = response.split("\r\n\r\n", 1)
    headers = parts[0][:200]   # 头部截 200 字符
    body = parts[1][:600]      # 正文截 600 字符
    # URL 路径放在最前面 → LLM 优先获得路径上下文
```

**5 条硬规则详解**:

| # | 规则 | 触发条件 | 原理 |
|---|------|---------|------|
| 1 | 技术识别保护 | `finding_type == "tech"` | 技术栈识别不是漏洞，AI 可能误判 |
| 2 | XSS 转义检测 | body 含 `&lt;script&gt;` 且不含 `<script>` | 已做 HTML 实体编码 = 安全 |
| 3 | 内部重定向 | Location 头以 `/` 开头 | 内部跳转 ≠ 开放重定向 |
| 4 | 调试已关闭 | body 含 "Debug Mode: OFF" 或 "redacted" | 已主动关闭调试功能 |
| 5 | Git 文字提及 | 提及 "Index of /.git" 但无 `<a href>` 链接 | 文字描述 ≠ 真实文件列表 |

**Bug 修复记录**:

1. **响应预览 Bug**: `response.split("\r\n\r\n")[0]` → 只拿到 HTTP 头部
   - 修复: `parts[0][:200]` + `parts[1][:600]` 分别取头和体
2. **`.format()` 注入**: 响应体含 `{` 时 Python 的 `.format()` 抛 KeyError
   - 修复: 改用 f-string：`f"分析以下 {count} 条..."`

## 4. 技术决策

### 决策 1: 为什么要批量分析而不是逐条？

| | 逐条 | 批量 |
|---|:--:|:--:|
| 耗时 | 5 分钟 | 1 分钟 |
| 准确率 | 低（无上下文） | 高（相对判断） |
| LLM 调用次数 | N 次 | 1 次 |
| 失败影响 | 单条失败可重试 | 整批失败需重来 |

**结论**: LLM 看到全部结果的上下文时，能更好地做相对判断（"哪些像真正的漏洞 vs 哪些像信息提示"）。

### 决策 2: 为什么用 8B 模型而不是 API？

| | 本地 8B | GPT-4 API |
|---|:--:|:--:|
| 费用 | 免费 | ~$0.03/次扫描 |
| 延迟 | 17-33s/批 | ~3s/批 |
| 数据隐私 | 不出本机 | 上传 OpenAI |
| 一致性 | 75-100% 波动 | 95%+ 稳定 |
| 部署难度 | 需要 5GB+ 显存 | 只需 API Key |

**结论**: 对于演示项目，零费用和数据隐私更重要。模型波动问题通过混合防线解决。架构上保留了切换 API 的能力。

### 决策 3: 为什么用 `http:` 而不是 `requests:` 格式？

Nuclei v3 支持两种模板格式：
- `http:` — 老格式，简洁（用于我们的自定义模板）
- `requests:` — 新格式，支持多协议组合（更复杂）

我们的模板只用 HTTP 协议，用老格式更简洁。注意 Nuclei v3.8 开始对老格式发 warn，但不影响使用。

### 决策 4: 为什么 BATCH_SIZE=5？

平衡点——对于 8B 量化模型：
- 太少（1-2）：浪费时间在多轮推理上
- 太多（10+）：模型不稳定，容易截断 JSON，准确率下降
- 5：单次推理 ~25s，JSON 解析稳定，AI 能充分关注每条结果

### 决策 5: 硬规则为什么是 5 条而不是更多？

硬规则的取舍：
- **确定性场景**才加规则（如 HTML 实体编码 = 绝对安全）
- **模糊场景**留给 AI（如教程页判断 = 语义理解）
- 规则太多 → 维护成本高，规则之间可能冲突
- 5 条刚好覆盖当前靶场的所有确定性误报场景

### Matcher 类型速查

| 类型 | 匹配对象 | 示例 | 适用场景 |
|------|---------|------|---------|
| `word` | 响应中的关键词 | `words: ["admin"]` | 页面内容检测 |

```yaml
!contains(to_lower(header), 'x-frame-options')

status_code >= 200 && status_code < 300

# 检查正文长度
len(body) > 0

# 正则匹配
contains(body, 'admin')

# 判断响应是否包含某字符串
contains(to_lower(header), 'nginx')
```

## 7. 追问清单

### Q: 为什么不用 Docker？

"Docker Desktop 在 Windows 11 Home China 环境启动失败，而且 Docker Hub 被墙。塞翁失马——自建靶场反而更有面试价值，因为它展示了'靶场设计能力'和'扫描检测能力'两个维度。"

### Q: AI 不可用时怎么办？

"架构支持优雅降级。如果 Ollama 连接失败，`filter_results()` 会返回空判定的默认结果（类型 unknown、非误报）。扫描仍然可用，只是没有 AI 判定。报告生成也有 fallback——纯代码统计生成基本摘要。"

### Q: 怎么扩展到生产环境？

"三个方向：第一，SCAN_HISTORY 从内存改数据库（SQLite/PostgreSQL）；第二，接入更大模型（qwen3:32b 或云端 API）提升稳定性；第三，支持 Nuclei 官方全量模板库，按指纹智能选择。"

### Q: 模板的 FP 干扰项怎么设计的？

"核心原理：页面 HTML 中保留模板匹配的字面量关键词，让模板先触发，再由 AI 来判定是真漏洞还是误报。比如教程页在 `<pre><code>` 中放未转义的 `<script>` 标签——Nuclei 匹配到关键词触发告警，AI 看到标题'XSS 入门教程'和代码块结构，判定为教学文章。"

### Q: 你怎么知道 AI 判得对？

"对照实验。先确认每个端点应该被判定为什么——漏洞列表是预先设计的。然后跑扫描，对比 AI 判定与预期。多轮测试记录波动性。8B 模型的一致性问题是重要的发现——直接导致了混合防线的设计。"
